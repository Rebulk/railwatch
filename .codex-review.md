# Adversarial review: is embedded Railwatch ready to ship?

You are reviewing a Ruby gem (`railwatch`) before it is published and marketed.
Effort: maximum. Be adversarial. I want logical holes, not style notes.

## What the gem is

Railwatch is a Rails observability gem (requests, jobs, queries, exceptions,
logs, cache, mail, outgoing HTTP). It has two modes:

- **cloud**: reporter thread POSTs batches to a hosted platform.
- **embedded** (`c.transport = :local`, what you are reviewing): batches are
  written into two SQLite databases the host app owns (`railwatch` for issues
  and saved views, `railwatch_telemetry` for telemetry), and the gem serves a
  full prebuilt Inertia/React dashboard from a mounted engine at `/railwatch`.
  No token, no cloud, no Node, and deliberately **no job worker**: a forked
  writer process owns the SQLite files and runs a maintenance clock.

The product promise, which a reviewer should treat as a hard invariant:
**Railwatch never writes the host application's own databases**, and it must
never take the host app down or leak the host's data.

## Specific suspicions I want you to confirm or kill

Do not stop at these; they are where I already smell trouble.

1. **`connects_to` is now conditional.** `Railwatch::ApplicationRecord` and
   `TelemetryRecord` call `connects_to ... if Railwatch.database_configured?(:x)`.
   If that predicate is ever false at class-load time in an app that DOES have
   the databases (boot ordering, a rake task, a console, `db:prepare` itself,
   eager load before `database_configuration` is memoized), those abstract
   classes silently fall back to the host's **primary** connection. Trace every
   path. Would the gem then write telemetry tables into the customer's own
   database? Is there a failure mode where it creates or migrates tables there?
   This is the invariant that matters most; be thorough.

2. **The Puma plugin now forks in single mode.** It used to refuse (comment
   said: in single mode the request threads are already running when we fork,
   and a fork from a multithreaded parent inherits locks held at that instant).
   I changed it to fork in both modes because a default Rails 8 app runs Puma
   with no workers. Solid Queue's plugin does the same thing, which is my
   precedent. Is that precedent actually sound here? The child opens SQLite
   connections and serves a Unix socket. What can the child inherit in a
   locked state (Active Record pool mutexes, logger, Zeitwerk, the reporter's
   own mutex)? Does `ActiveSupport::ForkTracker` / Active Record's own
   after-fork hook actually make this safe, or is there a deadlock window?

3. **Shutdown ordering in single mode.** Puma's `Launcher#do_graceful_stop`
   fires `after_stopped` and THEN calls `runner.stop_blocked` (which waits for
   in-flight requests). In cluster mode the SIGTERM trap stops workers first
   and fires `after_stopped` after. The plugin kills the writer from
   `after_stopped`. In single mode does that kill the writer while requests
   are still being served, so their telemetry is retained and then lost at
   exit? If so, what is the right hook?

4. **HTTP Basic gate coverage.** `DashboardController#authenticate_by_http_basic`
   is the only gate. Enumerate every route the engine mounts and every
   middleware it inserts, and find anything that reaches telemetry or the
   host's data without passing through it. I know of two on purpose:
   `BeaconController` (`ActionController::API`, an unauthenticated write path
   for browser timings, rate-limited by IP) and the `DashboardAssets`
   middleware serving `/railwatch/assets/*`. Are those actually safe? Can the
   beacon be used to forge telemetry, exhaust storage, or inject content that
   the dashboard later renders (stored XSS into an operator's browser)?

5. **`base_controller_class.constantize` at class-definition time.** The
   dashboard controller's superclass is resolved when the class body runs.
   Does that break Zeitwerk reloading in development, autoload-before-boot,
   or a host whose `AdminController` is itself autoloaded? What happens with
   a typo or a missing constant: a clear error or an unbootable app?

6. **The `json < 3` runtime dependency.** Added because Rails 8.1 cannot
   decode with json 3 (rails/rails#58784) and Ruby 3.4.10 ships json 3.0.2 as
   a default gem, which broke this gem's own migrations. Is a hard `< 3`
   dependency in a published gem the right call, or will it block installs for
   apps that need json 3 for something else? Is there a narrower fix?

7. **The installer runs migrations.** `prepare_local_databases` calls
   `ActiveRecord::Tasks::DatabaseTasks.with_temporary_pool_for_each` +
   `migrate` from inside a Rails generator, in whatever `RAILS_ENV` the
   generator ran in. Does it leak connections, clobber the host's
   `ActiveRecord::Base.configurations`, dump a schema file, or touch the
   host's own databases? Does it do the right thing when run twice, or when
   the app has no `config/database.yml`, or in an app using Postgres/MySQL for
   its primary?

8. **`Record.buffered_bytes` rewrite.** Perf change on the request path: the
   recursive walk was flattened so scalars are weighed inline in the container
   loops. Verify it is still equivalent for every shape (deep nesting,
   self-referential structures, non-Symbol hash keys, the early-exit at the
   byte limit) and that the depth bound still terminates a cycle.

9. **The `Writer.expected?` fix.** The socket transport used to capture "is a
   writer expected" at construction; under `rails server` the app boots (and
   builds the reporter) before Puma evaluates `config/puma.rb`, so every
   worker inherited `expected=false`, missed the socket once during writer
   startup, and fell back to in-process SQLite writes for the life of the
   worker. Now it reads the flag at delivery time. Is the new behaviour right
   in every process shape (runner, console, Solid Queue worker, test suite,
   a second Puma on the same host, a forked child of a worker)? Can it now
   retain forever in a process where no writer will ever appear?

## Also assess

- Anything that could **lose telemetry silently** or **report success when a
  batch was dropped**.
- Anything that could **take the host app down** (an exception on the request
  path, a boot failure, a deadlock, a wedged writer).
- Multi-process and multi-server correctness: two Puma masters on one host,
  a container restart sharing a volume, a phased restart, `kill -9`.
- Whether the docs (`docs/embedded.md`, `README.md`, `docs/configuration.md`)
  now match the code, especially the Authentication and Install sections.
