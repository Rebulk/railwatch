# Verdict

**DO NOT SHIP.** The reviewed commits improve the happy path, but embedded mode still violates two release invariants under concrete, ordinary failure modes: the Railwatch models fail open onto the host primary database, and single-mode Puma tears the writer down before in-flight requests finish. In addition, a writer that is expected but cannot bind causes bounded retries followed by silent loss; the one-command installer does not produce SQLite databases in a PostgreSQL/MySQL app; direct `puma` startup silently skips the writer; and the unauthenticated beacon can persist attacker-chosen telemetry and issues without a dependable rate limit. These are correctness/security failures, not polish.

# Blocking findings

1. **A missing or temporarily unavailable secondary configuration permanently binds Railwatch models to the host primary.**  
   **Files:** `app/models/railwatch/application_record.rb:16`, `app/models/railwatch/telemetry_record.rb:17`, `lib/railwatch.rb:582-587`  
   **Failure scenario:** Start embedded mode with either named entry absent/misspelled, or load either abstract class before `ActiveRecord::Base.configurations` contains that entry. `database_configured?` returns false (and converts every internal error to false), the `connects_to` call is skipped, and the class inherits `ActiveRecord::Base`'s primary pool for the lifetime of that class. Updating configurations later does not revisit the class body. `Transport::Local`, the writer, maintenance, dashboard mutations, and deploy recording then execute Railwatch model operations against the customer's primary connection. Most apps will get missing-table errors and lose telemetry, but an app with colliding unprefixed telemetry tables (`logs`, `queries`, `exceptions`, `executions`, etc.) or pre-existing `railwatch_*` tables can be read or written. This is enough to violate the hard invariant even though it requires a schema collision to make a write succeed. Normal Rails boot does populate `ActiveRecord::Base.configurations` before production eager loading, so I did not find a standard eager-load ordering failure; the concrete paths are missing/invalid/late-added configuration, all of which must fail closed rather than select primary. The reviewed migration paths do **not** create or migrate Railwatch tables in primary: `db:prepare` targets the named configs and their `migrations_paths`. The danger is runtime model access, not migration routing.  
   **Fix:** Never let either abstract class inherit the primary connection. Give it a lazy, explicit named connection that raises a Railwatch configuration error on first use if the named config is unavailable, or bind it to a deliberately unusable fail-closed specification until the named config exists. Do not rescue arbitrary errors into “use primary.” Add tests that load each base before/without the named config, then assert that `connection_db_config.name` is never `primary` and that a query fails before reaching the primary adapter.

2. **Single-mode graceful shutdown kills the writer before Puma drains in-flight requests.**  
   **File:** `lib/puma/plugin/railwatch.rb:125-143`  
   **Failure scenario:** Under Puma 8, `Launcher#do_graceful_stop` calls `events.fire_after_stopped!` and only then calls `runner.stop_blocked`; `Single#stop_blocked` is the operation that stops the server and waits for request threads. Thus the new `after_stopped` callback first shuts down the reporter and terminates the writer while requests are still running. A request that finishes afterward records telemetry into the same reporter. `Reporter#write` sees that its old thread is dead and starts a new one, but `Writer.expected?` remains true and the socket is now gone. Those records retry in memory and are lost when the Puma process exits. A request that was already finishing while the first reporter shutdown drained also races outside that drain. Cluster mode has different ordering and does not establish the single-mode claim.  
   **Fix:** Move the final reporter flush and writer termination to a point after `Single#stop_blocked` has returned. Puma exposes no post-drain event in this sequence, so use a Puma-supported lifecycle integration that actually runs after the runner drains, or an `at_exit` handler ordered so request/health/session producers are stopped before the reporter and writer. Keep cluster behavior separate if necessary. Add an integration test with a blocked Rack request: send TERM, allow the request to finish after `after_stopped`, and assert its execution is committed before the writer exits.

3. **“Writer expected” changes a permanent startup failure into silent, total telemetry loss.**  
   **Files:** `lib/puma/plugin/railwatch.rb:27-39,71-93`, `lib/railwatch/transport/socket.rb:56-77`, `lib/railwatch/reporter.rb:323-336`, `lib/tasks/railwatch_tasks.rake:135-145`  
   **Failure scenario:** Configure a usable-length socket path whose directory is not writable, or exhaust process/file resources so the writer cannot fork or bind. The plugin sets the process-global expected flag before any writer is ready. Each writer child exits and the supervisor retries, while every socket delivery returns a retryable error and is never allowed to fall back locally. Contrary to the transport/docs wording, retention is not indefinite: after `MAX_RETRY_ATTEMPTS` the reporter converts the batch to a dropped count and emits only a `RAILWATCH_DEBUG` line. If no delivery ever succeeds, even that count never leaves the process, and shutdown ignores a dropped-only buffer because `pending_records?` counts records, not drops. `railwatch:doctor` also reports the writer check as passing whenever `config/puma.rb` merely contains the plugin, even when the socket is not listening. The new late read of `Writer.expected?` is correct during a normal writer startup, and normal runner/console/test processes start with false; the failure is treating “configured” as permanent proof that a writer will eventually exist.  
   **Fix:** Add a parent/child readiness handshake and distinguish `starting`, `ready`, and `failed`; do not set the serving process to permanently expected until bind succeeds. If readiness cannot be achieved within a bounded startup/restart window, either fail Puma boot loudly or switch to an explicitly reported local fallback. A batch abandoned after the retry cap must call `on_unrecoverable`. Make doctor fail when the plugin is configured but the running writer is absent. Test bind `EACCES`, repeated child exit, fork failure, and a detached/forked descendant that inherited `expected=true` after its Puma parent disappeared.

4. **The one-command installer does not create SQLite databases for PostgreSQL/MySQL apps and can generate invalid YAML.**  
   **Files:** `lib/generators/railwatch/install/install_generator.rb:182-204,287-304,312-339`; `railwatch_specification.rb:41-53`  
   **Failure scenario:** Run `generate railwatch:install --local` in a normal app generated with `--database=postgresql` or `--database=mysql`. Both inserted Railwatch configs merge `*default` and never override `adapter`, so a path such as `storage/production_railwatch.sqlite3` is interpreted as a PostgreSQL/MySQL database name. `DatabaseTasks.migrate` does not perform the “prepare/create” operation advertised, the connection/migration fails, the generator rescues and continues, and every subsequent `db:prepare` sees the same bad adapter. Such an app also ordinarily has no `sqlite3` gem, and Railwatch does not depend on it. If a custom `database.yml` has no `&default` anchor, the generated `<<: *default` makes the whole file invalid. If there is no `database.yml` or no conventional `development`/`test`/`production` key, the generator warns/skips but still prints “Both databases were created just now.” The standard SQLite template is idempotent, uses temporary named pools, restores the original primary pool, honors `schema_dump: false`, and does not migrate primary; those parts are sound.  
   **Fix:** Decide and enforce the storage contract. For the promised SQLite files, emit self-contained configs with `adapter: sqlite3` rather than inheriting the host default, ensure a compatible `sqlite3` dependency is installed for local mode, create parent directories, and run actual create/prepare semantics before migrate. Alternatively, support the host adapter and generate valid adapter-specific database names/create operations. Abort the generator on missing/unsupported configuration instead of printing successful next steps. Add real generator integration tests for SQLite, PostgreSQL, MySQL, no anchor, no `database.yml`, nonstandard environment names, a second run, and a migration failure.

5. **The generated writer integration is silently disabled under direct Puma startup.**  
   **Files:** `lib/generators/railwatch/install/install_generator.rb:342-347`, `lib/puma/plugin/railwatch.rb:20-39,52-69`  
   **Failure scenario:** Start a deployed Rack/Rails app with the common `bundle exec puma -C config/puma.rb` path instead of `bin/rails server`. Puma evaluates its configuration and fires plugin `start` before loading the Rack application. The generated `plugin :railwatch if defined?(Railwatch)` is therefore skipped when the application has not already required the gem. Even if an operator activates the plugin unconditionally on the command line, `start` calls `active?` before the app/initializers have loaded and returns without installing any background task or lifecycle hook. Embedded telemetry then falls back to in-process SQLite writes in every web process; the promised writer and its single maintenance clock never exist. With multiple web workers this restores the contention and loss modes the writer is meant to remove.  
   **Fix:** Activate the plugin unconditionally in generated Puma config, and make plugin `start` register its hooks without requiring the Rails app to be loaded. Evaluate Railwatch/local configuration after the Rack app has loaded but before requests can flush, then establish writer readiness. Add boot tests for both `bin/rails server` and direct `bundle exec puma` in single and cluster modes.

6. **The public beacon is an attacker-controlled persistent write/issue-creation endpoint whose only limiter can fail open.**  
   **Files:** `app/controllers/railwatch/beacon_controller.rb:6,12-25,27-60,65-84,120-184`  
   **Failure scenario:** No dashboard authentication or CSRF/origin check applies to `POST /railwatch/beacon`. One request can create 50 visits, 50 unhandled browser exceptions, and a session; exception follow-ups create attacker-named issues. At the default 120 requests/minute this is up to 12,120 persistent rows and 6,000 exception occurrences/issues per minute per apparent IP, with as much as 256 KiB of attacker input per request. More importantly, the code explicitly fails open when the host cache cannot increment (including `NullStore`), making the rate unlimited; IP rotation also multiplies the nominal bound. The payload caps prevent a single-request allocation bomb, and I found no stored-XSS sink—React renders beacon messages, context, frames, and breadcrumbs as text—but they do not protect disk, issue integrity, grouping CPU, or the operator's trust in the data.  
   **Fix:** Require a verifiable browser capability (the already-sent CSRF token with request-forgery protection, a signed short-lived beacon token, or authenticated same-origin session), and use a limiter that fails closed and is independent of an optional host cache. Add a global storage/ingest budget as a second boundary. Consider disabling browser error ingestion by default in embedded mode until that gate exists. Test `NullStore`, spoofed/rotating addresses, cross-origin form requests, and sustained maximum-size payloads.

# Non-blocking findings

1. **The authentication task can shadow existing Rails credentials and cannot repair a partial auth config.**  
   **File:** `lib/railwatch/authentication.rb:19-32,52-73`  
   **Scenario:** With an existing `railwatch:` mapping containing some other secret, `configure` appends a second top-level `railwatch:` key. Psych resolves duplicate mapping keys to the later value, so existing nested values disappear from `app.credentials` even though their text remains encrypted in the file. An unquoted username containing YAML syntax can also alter the generated shape. Conversely, if only user or only password exists, `configured?` uses `any?`, refuses to run, and leaves the dashboard closed.  
   **Fix:** Parse and merge the existing credentials mapping, quote scalar values through YAML serialization, and consider auth configured only when both values exist; otherwise repair the missing half or give a precise error.

2. **`Record.buffered_bytes` no longer has the same result at the depth boundary.**  
   **File:** `lib/railwatch/record.rb:56-107`  
   **Scenario:** The old routine checked `depth > 8` before dispatching every value. The rewrite checks depth only on arrays/hashes and weighs scalar values inline. Nine nested arrays ending in `"x"` with limit 10,000 previously return 10,001 (too deep) and now return 473. Deep symbol/non-symbol scalar hash keys change similarly. Cycles still terminate because the repeated container crosses the bound, and normal flat records retain the optimized numbers, so this is not a cycle or common-path blocker.  
   **Fix:** Apply the depth check before inline scalar/key accounting (or explicitly redefine and test the new semantics). Add equivalence/property tests against the prior implementation, including depth 8/9, container keys, cycles, finite limits, and `Float::INFINITY`.

3. **A host base controller or mount constraint does not protect the Action Cable channel when Basic is disabled.**  
   **Files:** `app/channels/railwatch/environment_channel.rb:6-16`, `lib/railwatch/configuration.rb:298-309`, `docs/embedded.md:103-130`  
   **Scenario:** `c.base_controller_class` applies only to HTTP controllers, and a route constraint around `/railwatch` does not wrap the host's separate `/cable` endpoint. With Basic disabled, `http_basic_auth_ok?` returns true unconditionally, so anyone allowed to open the host Action Cable connection can subscribe to `EnvironmentChannel` id 1. The event contains only ingest time/counts, not telemetry records, so this is metadata leakage and fan-out potential rather than dashboard data disclosure. A host-level `ApplicationCable::Connection` gate may independently close it, but the documented base-controller/mount options do not.  
   **Fix:** Provide a channel authorization callback tied to the host's connection/session, or disable live updates when Basic is off unless one is configured. Document that a route constraint does not cover `/cable`.

4. **Malformed Basic credentials can raise out of an Action Cable subscription.**  
   **File:** `lib/railwatch/configuration.rb:302-309`  
   **Scenario:** `ActionController::HttpAuthentication::Basic.authenticate` splits decoded credentials on the first colon. A header whose decoded value has no colon calls the block with `password=nil`; `SecurityUtils.secure_compare(password, ...)` then calls `nil.bytesize` and raises `NoMethodError`. The dashboard controller uses Rails' safer helper, which converts both submitted values to strings, but the channel path does not. This is remotely triggerable when the cable endpoint is exposed, although Action Cable should contain it to the offending subscription.  
   **Fix:** Compare `user.to_s` and `password.to_s`, and return false on malformed authentication. Add missing-colon, invalid-base64, empty-user, and empty-password channel tests.

5. **A writer can terminate a still-running batch after five seconds despite the new “finishes the batch first” comment.**  
   **Files:** `lib/puma/plugin/railwatch.rb:114-116`, `lib/railwatch/writer.rb:224-226`  
   **Scenario:** TERM closes the accept socket, but `serve` joins each worker for only five seconds. `run!` then reaches its ensure block and the fork wrapper calls `exit!`, killing any longer batch thread. The SQLite transaction should roll back and a live client can retry by batch id, so this is recoverable during ordinary operation; combined with the premature single-mode shutdown in blocking finding 2, the client may itself be exiting.  
   **Fix:** Drain in-flight workers to the documented wedge deadline, or explicitly abort them and keep the client/reporter alive long enough to retry. Make the shutdown guarantee and timeout agree.

## Suspicions checked and not found to be defects

- **Fork safety:** I did not find the proposed inherited-Ruby-lock deadlock. MRI reinitializes `Mutex`/`Monitor` state in the child; Rails 8.1's `ForkTracker` invokes Active Record's `PoolConfig.discard_pools!`, and Railwatch replaces its reporter/flush mutexes without taking the inherited ones. The Solid Queue plugin does use the same post-boot fork shape. Native third-party libraries can always have fork restrictions, but there is no concrete failure in this diff to report. The lifecycle and inherited-listener cleanup deserve integration coverage, but speculation is not a blocker.
- **`base_controller_class.constantize`:** Engine and host controller paths are both managed by Rails' main (reloadable) Zeitwerk loader, so unloading reloads the subclass and its configured superclass together. Initializers run before first autoload/eager load. A typo produces a direct `NameError` (during eager load in production, on first access in development); harsh, but clear. Changing the setting after the controller has loaded naturally requires reload/restart.
- **HTTP Basic controller coverage/assets/XSS:** Every telemetry-reading or mutating engine controller inherits `DashboardController`. The other HTTP paths are redirect routes, the beacon, and `DashboardAssets`. Assets serve only the shipped content-hashed bundle/fonts/icons/manifests; no source maps are present, and the traversal check rejects decoded `..`. Beacon-controlled strings reach React text nodes, not either `dangerouslySetInnerHTML` site, so I found no stored XSS. The beacon storage/integrity problem remains blocking finding 6.
- **`json < 3`:** Rails 8.1.3.1 still calls `JSON.parse(json, options)` positionally, which is incompatible with json 3's keyword signature. Pinning `< 3` is ecosystem-wide and can conflict with an app that explicitly needs json 3, but such an app is already incompatible with the supported Rails line's JSON decoding. The pin is defensible as a temporary compatibility constraint; remove or narrow it when the minimum Rails version contains the upstream fix.
- **Installer pool/schema behavior on the supported SQLite-template path:** `with_temporary_pool_for_each(name:)` switches only `ActiveRecord::Base`'s temporary migration pool and restores the original config in ensure; the code selects only the two named databases and does not dump schemas. Re-running migrations is idempotent. The blocking installer defect is adapter/config generation, not a demonstrated primary migration or pool leak.

# Things I claimed that are wrong

1. **“Nothing is lost” / Puma reporters “retry for as long as it takes.”** `docs/embedded.md:183-190` and `lib/railwatch/transport/socket.rb:20-24` conflict with `Reporter::MAX_RETRY_ATTEMPTS` and `Reporter#retain`, which discard after eight retries. With a permanently failed expected writer, loss is silent unless debug logging is enabled.

2. **`after_stopped` means single-mode requests are already through.** The comment at `lib/puma/plugin/railwatch.rb:125-130` is the reverse of Puma 8's order: `after_stopped` fires before `Single#stop_blocked` waits for requests.

3. **TERM finishes a batch before the writer exits.** `lib/puma/plugin/railwatch.rb:114-116` omits the five-second worker join limit at `lib/railwatch/writer.rb:224-226`.

4. **The local install is one command that creates/migrates both SQLite databases and boots in production.** `CHANGELOG.md:91-100`, `docs/embedded.md:24-27`, and the generator's success message are false for PostgreSQL/MySQL defaults, configs without `&default`, missing/nonstandard `database.yml`, and apps without the sqlite3 gem.

5. **“No web process ever holds the telemetry database” / every configured Puma uses the writer.** `lib/generators/railwatch/install/install_generator.rb:217-222` and `docs/embedded.md:147-169` are false for direct `bundle exec puma`: the generated conditional skips plugin activation before the app is loaded, and early `active?` would disable it even if activated externally.

6. **The database predicate reads “raw configuration.”** `lib/railwatch.rb:579-587` actually reads `ActiveRecord::Base.configurations`, then hides all errors as false. More importantly, false means primary inheritance rather than an inert/fail-closed model.

7. **“Every page and the live channel answer 401” when credentials are absent.** `CHANGELOG.md:101-104` overstates the implementation. Controller-backed dashboard pages return 401; root/dashboard/docs/application redirects happen in the router without the controller gate, assets remain public, the beacon remains public, and an Action Cable subscription is rejected rather than returning an HTTP 401 with the explanatory note. None of the redirect/asset exceptions exposes telemetry.

8. **A base controller or route constraint is also the live-channel gate.** The comment at `app/channels/railwatch/environment_channel.rb:8-10` is false because neither mechanism wraps `/cable`; turning Basic off makes the channel check unconditional true.

9. **The sizing rewrite has “same numbers, same depth bound.”** `CHANGELOG.md:130-134` is false at deeply nested scalar leaves and hash keys, as described in non-blocking finding 2.
